# IMTS Complete Development Plan

## 1. Purpose and source of truth

This document is the implementation roadmap for the Bank of Uganda Innovation Management Tracking System (IMTS). It converts the requirements in `Innovation Management System Requirements.pdf` into an ordered engineering plan for the current ASP.NET Core repository.

When sources disagree, use this priority:

1. The approved SRS and written change requests.
2. Security and data-integrity requirements.
3. This development plan.
4. Existing working code.
5. Design-reference HTML mockups.

A mockup is not a functional requirement and must never override authorization, validation, MVC routing, or database rules.

## 2. Product outcome

IMTS replaces manual innovation processing with an on-premises web application that supports:

- Staff idea submission and personal tracking.
- Innovation Team review and workflow management.
- IT Administrator account, role, and audit administration.
- Attachments, comments, notifications, resources, reports, timelines, and auditability.
- Deployment on Windows Server, IIS, and Microsoft SQL Server.

## 3. Required user roles and authority

| Role | Role value | May access | Must never access |
|---|---|---|---|
| Staff | `Staff` | Own dashboard, own drafts, own ideas, permitted resources, own notifications | Other Staff members' private ideas, review decisions, administration |
| Innovation Team | `InnovationTeam` | All submitted ideas, reviews, categories, timelines, reports, resources | IT-only account/security operations unless separately authorized |
| IT Administrator | `Admin` | Accounts, roles, permissions, audit logs, system settings | Business review decisions unless separately assigned |

Rules:

- Server-side authorization is mandatory. Hiding a link is not authorization.
- Staff ownership must always come from `ClaimTypes.NameIdentifier`; never trust a user ID from a URL or form.
- Every query returning personal data must apply an ownership or authorized-role predicate.
- Every state-changing action must use POST, anti-forgery validation, and server-side validation.

## 4. Architecture contract

```text
HTTP request
  -> MVC Controller
  -> Application repository/service
  -> EF Core DbContext
  -> SQL Server
  -> View model
  -> Razor view
  -> HTML response
```

### Layer responsibilities

| Project | Responsibility | Forbidden responsibility |
|---|---|---|
| `Template.Common` | Enums, constants, shared audit abstractions | EF queries, controllers, Razor models |
| `Template.Data` | Entities, DbContext, relationships, migrations, seed data | UI formatting and HTTP behavior |
| `Template.Core` | Repositories, application services, application DTOs, authorization logic | Razor markup and browser scripts |
| `Template.Web` | Controllers, web view models, Razor views, static assets | Reusable business rules and unrestricted raw queries |

### Implementation rules

- Controllers coordinate requests; repositories/services own reusable data and business operations.
- Read-only EF queries use `AsNoTracking()`.
- Async database APIs are used end-to-end.
- Entities are never posted directly from forms; bind dedicated input/view models.
- Use explicit projections instead of loading full graphs unnecessarily.
- All list pages support bounded pagination.
- All external file paths are generated by the server and validated before access.
- Use Post-Redirect-Get after successful form submissions.
- Do not create a migration for view-only, CSS-only, or repository-only work.
- Create one reviewed migration for each intentional schema change.

## 6. Workflow state machine

The workflow must be coded as explicit allowed transitions. Do not permit arbitrary string changes.

### Stages

```text
Submitted
  -> ConceptDevelopment
  -> Experimentation (when required)
  -> Deployment
  -> Closed
```

Permitted alternative:

```text
ConceptDevelopment -> Deployment
```

Use the exact names defined in `IdeaStage`. Display-friendly labels belong in view helpers, not in stored values.

### Statuses

Use the exact values defined in `IdeaStatus`, including the intended equivalents of:

- Under review
- Pending information
- Approved
- Declined

### Default stage timelines from the SRS

| Stage/activity | Default duration |
|---|---:|
| Idea selection | 30 days |
| Concept development | 60 days |
| Experimentation/research | 90 days |
| Launch after approval | 30 days |

### Transition requirements

Every stage/status change must:

1. Confirm the current user has Innovation Team authority.
2. Load the tracked idea and its current open timeline.
3. Validate the requested transition against an allowed-transition map.
4. Check optimistic concurrency using `RowVersion`.
5. Complete the old timeline when the stage changes.
6. Create or update the new timeline and deadline.
7. Add a `StageHistory` record containing old/new stage and status.
8. Add a submitter notification.
9. Write an audit event.
10. Save the entire change atomically in one transaction.

### Exit gate

## Phase 3 - Staff idea lifecycle

### SRS coverage

IMTS-REQ-001, 010, 015, 020, 025, 030, 035.

### 3.1 Submission

1. Add data annotations and server validation to `SubmitIdeaModel`.
2. Load categories from active database records instead of hard-coded radio options.
3. Save every required SRS field. If entity fields are missing, design and review a migration first.
4. Support individual and team submissions with a defined team-member data model.
5. Validate attachment extension, size, count, MIME signature, safe filename, and storage path.
6. Store files outside `wwwroot`.
7. Save idea, initial timeline, attachments, notification, and audit event atomically.
8. Display a reference number only after commit succeeds.

### 3.2 Drafts

1. Define draft ownership and expiration rules.
2. Implement Save Draft, Edit Draft, Submit Draft, and Delete Draft.
3. Never show another user's drafts.
4. Validate again when a draft becomes a submitted idea.

### 3.3 View and amend

1. Staff may view only their own ideas.
2. Staff may edit only while the idea is unlocked and in an allowed stage/status.
3. Use `RowVersion` to detect concurrent changes.
4. Record changed fields in audit history.

### 3.4 Retract and cancel

1. Define exact business difference:
   - Retract: remove from active review while preserving the record.
   - Cancel: terminal user cancellation after allowed preconditions.
2. Enforce allowed states server-side.
3. Require confirmation in the UI.
4. Notify assigned reviewers when relevant.
5. Never hard-delete an idea with history.

### Tests

- Staff A cannot view/edit/download/comment on Staff B's idea.
- Invalid files, oversized files, and traversal filenames are rejected.
- Refresh after submit does not duplicate the idea.
- Locked ideas cannot be edited.
- Concurrent edits show a conflict message rather than silently overwriting.

### Exit gate

All Staff requirements work using two separate Staff test accounts, proving ownership isolation.

## 10. Page completion checklist

- Does it use `_Layout.cshtml` without nested document tags?

- Is the controller/action authorized server-side?
- Are input and output models strongly typed?
- Are all POSTs anti-forgery protected?
- Is validation shown next to fields and summarized when necessary?
- Are empty, loading, success, error, forbidden, and not-found outcomes handled?
- Is pagination bounded and filters preserved?
- Is the page keyboard accessible and responsive?
- Does it work without public CDN access?
- Do direct-route and ownership tests pass?
- Does the relevant audit/notification behavior occur?

## 11. Pull request and commit discipline

Use small, reviewable commits, for example:

```text
feat(categories): add authorized category repository and MVC actions
feat(categories): convert category mockup to functional Razor view
test(categories): cover uniqueness and safe deactivation
```

Each pull request must include:

- SRS requirements covered.
- User roles affected.
- Screenshots for UI changes.
- Migration details, or “No migration required.”
- Security/ownership analysis.
- Tests run and results.
- Known limitations and follow-up issues.

Never mix unrelated formatting, generated binaries, PDFs, or user changes into a feature commit.

## 12. Definition of ready

A task is ready only when:

- The SRS requirement and user role are known.
- Business rules and edge cases are written.
- Required data fields are identified.
- Authorization and ownership rules are explicit.
- UI reference and acceptance criteria are available.
- Dependencies and migration impact are known.

## 13. Definition of done

A feature is done only when:

1. Functional behavior matches the SRS.
2. Server-side authorization and ownership rules are enforced.
3. Validation and error handling are complete.
4. Data changes are transactional and auditable.
5. Notifications are generated where required.
6. UI uses the shared responsive design system.
7. Unit/integration/MVC tests cover happy and failure paths.
8. `dotnet build Template.sln --no-restore` succeeds with zero new errors.
9. `git diff --check` passes.
10. Manual role-based smoke tests pass.
11. Documentation is updated.
12. No known high-severity security or data-loss issue remains.
